OT TRAFFIC SIMULATION PLATFORM – ARCHITECTURE SPECIFICATION (PLAIN TEXT)

1. PURPOSE

Design and implement a premium, next-generation Operational Technology (OT) Traffic Simulation Platform that generates hyper-realistic, protocol-accurate network traffic for industrial environments. The system does not require PCAP ingestion but must support future extension modules for PCAP-based enrichment.

The platform must provide deep device fingerprinting, advanced protocol modeling, scenario generation, vertical templates, realistic addressing, and a modern drag-and-drop scenario studio with an embedded AI assistant powered by OpenAI.

2. CORE CAPABILITIES

2.1 Device Profile Generation
The system must support creation and management of hyper-realistic device profiles:

* Device type and functional role (PLC, HMI, historian, drive, sensor, RTU, relay, engineering workstation, etc.)
* Supported protocols and protocol stack behavior
* Timing models, jitter characteristics, polling rates
* Payload structure definitions and realistic value distributions
* Behavioral signatures specific to OT verticals
* Vendor-like fingerprints (abstracted where required)

2.2 Communication Profile Generation
Define deep communication behaviors including:

* Stateful protocol conversations
* Multi-step request/response patterns
* Timing, jitter, exceptions
* Polling cycles and operational phases (startup, steady, maintenance, shutdown)
* Communication behavior defined without requiring PCAPs but able to incorporate PCAP enrichment later

2.3 Traffic Synthesis
The system must generate highly realistic traffic:

* Packet-accurate and protocol-valid
* Timing-accurate with realistic inter-arrival distributions
* Exportable as PCAP or output as live packets
* Stateful conversation engines drive traffic behavior

2.4 AI-Driven Scenario Composition
Integrate OpenAI as a scenario composition engine to:

* Propose device mixes and communication flows
* Design realistic OT environments for several verticals
* Suggest timing adjustments, variations, and anomalies
* Produce machine-readable ScenarioPlan definitions in JSON form

Sensitive identifiers must be sanitized before being sent to OpenAI.

3. PROTOCOL ENGINES

Implement deep protocol-aware packet generators for OT protocols including but not limited to:

Initial required support:

* Modbus TCP (function codes, exceptions, register-level behavior)
* Profinet (DCP, RTC, RTA, I/O cycles, startup sequences)
* EtherNet/IP and CIP (Forward Open/Close, implicit and explicit messaging, assembly objects)

The architecture must allow extension to additional protocols such as OPC UA, DNP3, IEC-104, BACnet, ICCP, etc.

Protocol engines must:

* Construct valid OT protocol packets
* Maintain stateful conversation logic
* Produce realistic multi-step sequences consistent with real-world environments

4. VERTICAL-SPECIFIC TEMPLATES

Provide template environments for:

4.1 Water/Wastewater

* SCADA, RTUs, lift stations
* DNP3 and Modbus polling
* Central plant and remote site patterns

4.2 Manufacturing

* High-speed Profinet and EtherNet/IP
* PLCs, HMIs, drives, sensors
* Startup, steady-state, and changeover phases

4.3 Energy/Power

* Substation RTUs and protective relays
* IEC-104 and DNP3 traffic
* Event bursts and periodic reporting

4.4 Oil and Gas

* Remote well pad and pipeline SCADA
* Modbus and OPC UA traffic
* Sparse but predictable polling patterns

Users must be able to fully customize each template.

5. REALISTIC ADDRESSING AND TOPOLOGY

5.1 MAC Address Assignment

* Realistic vendor-like OUIs and MAC ranges
* Consistent identity assignment across scenario instances
* Ability to specify vendor families or genericized patterns

5.2 IP Address Assignment

* IPv4 private networking
* Subnets per OT zone (Plant Floor, DMZ, Corporate, Remote)
* Automatic or manual assignment

5.3 VLANs and Segmentation

* VLAN assignment to devices or groups
* Logical zone modeling for segmentation and routed boundaries

5.4 Topology Awareness

* Logical L2 and L3 representation
* Optional representation of switches, routers, and segmented environments

6. SCENARIO STUDIO (UI/UX)

6.1 Drag-and-Drop Canvas

* Visual builder for creating OT environments
* Drag devices from a palette
* Connect them with protocol flows
* Group devices by vertical, zone, VLAN, or logical function
* Support zoom, pan, selection tools

6.2 Property Panels
Devices must expose editable properties:

* Device role and type
* Supported protocols
* MAC/IP/VLAN settings
* Timing and behavioral models

Flows must expose:

* Protocol-level configuration
* Function code or session-level details
* Timing and anomaly injection options

6.3 Timeline and Phase Editor

* Adjust startup, steady-state, maintenance, and shutdown phases
* Allow scheduling of events and intensity modulation

7. EMBEDDED AI ASSISTANT (MCP SERVER)

The Scenario Studio must include an integrated AI assistant powered by an MCP server. The MCP server must:

* Expose full scenario graph (devices, flows, addressing, phases)
* Provide read/write access for AI-driven refinement
* Support programmatic actions (add device, add flow, adjust protocol settings, optimize realism, validate topology, generate scenario)

The AI assistant must:

* Suggest realistic flows and missing behaviors
* Recommend addressing schemes aligned with the vertical
* Complete protocol-level details based on industry norms
* Score scenario realism and highlight inconsistencies
* Allow natural language refinement of the scenario

The AI assistant must not be a passive chatbot; it must interact directly with the system through MCP.

8. TRAFFIC GENERATION ENGINE

Inputs:

* Scenario definition
* Protocol engines
* Addressing models
* Timing and behavioral models
* AI-generated ScenarioPlan

Outputs:

* PCAP files containing synthetic OT traffic
* Optional real-time packet generation

Requirements:

* Accurate timing simulation
* Stateful protocol behavior
* Support for large and long-running simulations
* Protocol validity and adherence to state machines

9. EXTENSIBILITY: OPTIONAL PCAP INGESTION MODULE

Although not required in the initial platform, the design must allow a future PCAP ingestion module capable of:

* Parsing PCAP files
* Extracting or refining device and communication profiles
* Merging new insights into existing fingerprint libraries
* Enhancing realism scoring

This module must be cleanly decoupled from the core simulation functions.

10. NON-FUNCTIONAL REQUIREMENTS

* Modern UI (React or similar)
* Modular or microservice architecture
* API-first design
* Strong and stable internal schemas
* Automated testing for protocol engines, scenario generation, and addressing logic
* Maintainability, readability, and extensibility
* Comprehensive documentation

11. DELIVERABLES

12. Architecture blueprint (service diagram, data flow, component definitions)

13. Data models for: DeviceProfile, ProtocolProfile, ProtocolEngine, CommPattern, FlowProfile, ScenarioPlan, addressing/topology models

14. Core libraries: device/profile library, protocol engines, realistic MAC/IP/VLAN assignment logic

15. Scenario Studio prototype including canvas, palette, property panels, scenario load/save

16. AI integration using MCP server and OpenAI scenario composer

17. Traffic generator capable of producing realistic PCAP output

18. Documentation including README, example vertical scenarios, unit and integration tests, and claude files
