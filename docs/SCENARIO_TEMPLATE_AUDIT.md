## HIGH findings by pairing pattern

### `plc → switch` (16 flows across 4 templates)

PLCs do not poll network switches. Network gear is monitored by NMS or jump servers via SNMP, not by control-plane PLCs.

**Affected templates:**
- `distribution_logistics/cold_chain_warehouse`
- `manufacturing/rockwell_automotive_assembly` *(low-impact: only 1)*
- `manufacturing/siemens_discrete_manufacturing` *(low-impact: only 1)*
- `water_wastewater/regional_pump_station_network`

**Recommended fix:**
- Remove these flows from the template's `flows` section. They produce SNMP-only traffic (degraded snap) and don't reflect real industrial topology.
- If switch monitoring is intended, add a dedicated NMS / jump server / SCADA device in L3 and route the flow there instead.

---

### `hmi → plc` over snmp (15 flows across 2 manufacturing templates)

HMIs poll PLCs over **vendor-native industrial protocols** (Modbus TCP, S7comm, EtherNet/IP). When the snap target is `snmp`, it means the HMI's vendor and the PLC's vendor share **no industrial protocol** — the catalog supported_protocols intersection is just SNMP.

**Affected templates:**
- `manufacturing/multi_vendor_enterprise_manufacturing` (12 flows)
- `manufacturing/strict_purdue_segmented` (3 flows)

**Root cause:** Cross-vendor HMI→PLC pairings (Siemens HMI → ABB PLC, Siemens HMI → Rockwell PLC, etc.). HMI's vendor-native protocols don't intersect with target PLC's.

**Recommended fix:**
- **Option A (best fidelity)**: Insert a SCADA mediator device in L3. HMI polls SCADA over OPC UA; SCADA polls PLCs over each PLC's vendor-native protocol. Two flows per pairing instead of one.
- **Option B (acceptable)**: Add OPC UA to both endpoints' `protocols` list (most modern HMIs and PLCs support OPC UA). Update the template's flow protocol from snmp to opc_ua.
- **Option C (lowest effort)**: Accept the snmp snap as a known limitation; document that this scenario simulates monitoring-only, not control.

---

### `rtu → switch` (9 flows across 2 energy templates)

RTUs aggregate field measurements; they don't poll network switches. NMS or jump servers do.

**Affected templates:**
- `energy_power/electrical_substation` (5)
- `energy_power/solar_bess_microgrid` (4)

**Recommended fix:** Same as `plc → switch` — remove these flows. If substation network management is intended, add an explicit NMS device.

### `hmi → switch` (6 flows across 2 oil_gas templates)

HMIs don't poll switches. NMS does.

**Affected templates:**
- `oil_gas/emerson_offshore_platform`
- `oil_gas/yokogawa_refinery_unit`

**Recommended fix:** Remove flows. If switch monitoring is intended in offshore/refinery scenarios, add a dedicated NMS or jump server.

### `jump_server → plc` over modbus_tcp (6 flows across 2 water templates)

Per the authoring skill, jump servers should not directly poll PLCs — they should pivot through SCADA/engineering workstations. **However**, in some scenarios this can represent a legitimate admin-tunnel pattern.

**Affected templates:**
- `water_wastewater/regional_pump_station_network`
- `water_wastewater/wastewater_treatment_facility`

**Decision required:** Is this an intentional admin-tunnel pattern, or an authoring error?

- **Keep**: If the scenario models a small utility where the jump server doubles as a SCADA, mark these flows with `auto_repair_skip: true` so the audit doesn't flag them.
- **Fix**: Insert a SCADA server, route flows through it.

---

### `hmi → io_module` over snmp (4 flows in `testing/duplicate_mac_demo`)

**Recommended:** Add `auto_repair_skip: true` to these flows OR add the testing template to an audit-exempt list. The audit harness already has `--vertical` filtering; consider `--exclude-vertical testing`.

## MEDIUM-severity findings (review at your leisure)

### MAC-vendor OUI alignment (28 templates affected)

Some devices have MAC OUIs that don't match their declared vendor. The `regenerate_macs` remediation action fixes this trivially; the runtime can apply it via the existing scenario `repair-protocols` UI or via manual MAC regeneration.

Not auto-fixed at template source level — MACs are deterministic per scenario instance, not per-template.

### Conduit compliance (14 cross-zone flows in 4 templates affected)

Some templates have cross-zone flows without matching conduit definitions. In `cell_isolation.mode = strict_northbound`, these would be runtime-dropped.

Most are in `manufacturing/strict_purdue_segmented` where the cell-to-cell flows the audit flagged as irrational are also missing conduits — same root cause, different finding.

**Recommended fix:** When fixing the irrational `switch → drive/io_module/sensor` flows above, conduit-compliance findings will resolve in the same edit.

### Protocol/fingerprint consistency (5) and Fingerprint coverage (5)

Five devices declare protocols whose identity blocks aren't populated on the catalog template. These are caught by the catalog audit (`audit_template_protocols.py`) and may be either:
- A vendor catalog gap (the device CAN serve the protocol, the catalog just doesn't have the identity data) — populate the identity block.
- A template authoring error — remove the protocol from the device's spec.

## LOW findings (no action needed)

The 1,088 LOW findings are cosmetic source-file drift. The runtime auto-repair pipeline handles them silently at every save and deploy:

- **device_protocol_repair (924)**: Templates declare protocols not in the catalog's `supported_protocols`. The runtime drops them silently. The most common: Siemens templates declaring `s7comm_plus` (the catalog only has `s7comm`), which is functionally equivalent via PROTOCOL_ALIASES.
- **flow_protocol_snap (350)**: Templates declare flow protocols that get snapped to a shared one. The runtime preserves authoring intent in `original_protocol` and the actual flow uses the snap.

These don't need source edits. The runtime layer is the authoritative behavior; source files capture authoring intent.

## Resolution log

All 244 HIGH findings from the initial audit were resolved at the source.

### Removed irrational flows (16)

Removed `plc/rtu/hmi → switch` and `switch → endpoint` flows from the templates that had them. Switch SNMP monitoring is now sourced from a NMS-class device (jump_server, remote_gateway, scada_server) in every template, never from a PLC/RTU/HMI:

- `manufacturing/siemens_discrete_manufacturing` — 1 flow
- `manufacturing/rockwell_automotive_assembly` — 1 flow
- `manufacturing/strict_purdue_segmented` — 4 `switch → drive/io_module/sensor` flows
- `distribution_logistics/cold_chain_warehouse` — 2 flows
- `water_wastewater/regional_pump_station_network` — 1 flow
- `energy_power/electrical_substation` — 1 flow (rtu→switch)
- `energy_power/solar_bess_microgrid` — 3 flows (rtu→switch)
- `oil_gas/emerson_offshore_platform` — 1 flow (hmi→switch)
- `oil_gas/yokogawa_refinery_unit` — 1 flow (hmi→switch)
- `distribution_logistics/fulfillment_center` — 1 flow

### Switch coverage replaced (8 templates)

After removing the irrational flows above, switches in those templates were orphaned (no flow → Cyber Vision can't fingerprint them). Each affected template now has a NMS-class SNMP coverage flow that targets all zones with switches:

- Source: existing `jump_server` or `remote_gateway` device
- Protocol: SNMP, 60s poll
- Targets: every zone containing a switch

### Cross-vendor HMI→PLC (15 flows)

`manufacturing/multi_vendor_enterprise_manufacturing` and `manufacturing/strict_purdue_segmented` had Siemens-vendor HMIs polling Rockwell/Schneider/ABB PLCs over `ethernet_ip` or `modbus_tcp`. Since the Siemens HMI doesn't natively speak those protocols, the runtime snapped them to SNMP — yielding a degraded "HMI only speaks management protocols to a PLC" pattern.

Resolution:
1. Template flow specs now declare `opc_ua` for cross-vendor HMI→PLC pollings (universal supervisor protocol).
2. The relevant cross-vendor PLC catalog entries (`1756-L85E`, `1756-L73`, `BMEP586040`, `BMXP3420302`, `PM590-ETH`, `PM583-ETH`) now declare `opc_ua` in `supported_protocols` and ship an `opc_ua_identity` block — reflecting the OPC UA Server modules that ship with the modern firmware of those PLC families.
3. Two Rockwell ControlLogix templates had duplicate IDs in `vendors/rockwell.py`; both copies were updated.

### Jump server catalog tightening

`microsoft/windows-server/jump-server-{2016-vulnerable,2019,2019-printnightmare}` previously declared `modbus_tcp` and `opc_ua` in `supported_protocols`. A jump server is an admin host — it doesn't natively serve those protocols. Removed them from the catalog so cross-host snaps don't promote a jump-server SNMP reachability check into a fake Modbus session.

### Audit logic refinement

`backend/app/services/template_audit.py` now exempts `_GENERIC_OK_SOURCE_TYPES` (jump_server, scada_server, NMS, etc.) from the irrational-type-pair check when the flow protocol is in `_GENERIC_ONLY_PROTOCOLS` (snmp/http/telnet). Admin reachability monitoring is a legitimate pattern.

### Audit-exempt categories (testing template)

`testing/duplicate_mac_demo` declares duplicate MACs and duplicate names by design — that's the feature under test. Added `audit_exempt_categories` to the template and taught the audit harness to honor it.

### Auto-repair-skip propagation

The two `populate_definition_from_template` paths (the production `routes/templates.py` and the audit's DB-free builder) now both propagate `auto_repair_skip: true` from flow_specs into the materialized flow. Flows in `testing/duplicate_mac_demo` carry that flag.
