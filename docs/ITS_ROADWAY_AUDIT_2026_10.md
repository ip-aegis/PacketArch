# ITS / Roadway / Intersection Audit

**Date**: 2026-10-21
**Scope**: Roadway, intersection and traffic-operations devices, protocols, scenarios and attack use cases on `master` (475fbb8)
**Companion plan**: `tasks/its-roadway-remediation-plan.md`

## Summary

PacketArch has a credible ITS *topology* layer: 4 hand-authored road templates, 3 archetypes (ATMS corridor, tunnel, toll plaza) and ~31 ITS-flavoured device templates. But the traffic it puts on the wire is not ITS traffic:

- **No NTCIP reaches the wire.** Every signal controller, DMS, RWIS, camera and toll device answers only the five MIB-II `system` objects. I executed this end to end on the archetype PCAP path. I confirmed it statically on the hand-authored-template path and the live-agent path. A DPI tool sees "an SNMP device", never "a signal controller in phase 2+6 green" (§1).
- **The NTCIP code that exists is wrong in three independent ways.** Nothing selects it, it is filed under the wrong OID arcs, and it matches OIDs by a broken substring test, so every value comes back `0`.
- **The device identities have errors a domain expert would spot.** SICAM CP-8000 (an energy RTU) appears as traffic central. A LOGO! 8 CVE is attached to the M60 controller. Several PENs belong to the wrong organisations (Málaga University, Mirapoint, Belo Corp, Dunes). The Pelco camera carries Schneider OUIs. A switch and an RTU are typed as traffic controllers. The ATMS master is Geo SCADA.
- **Use-case coverage is narrow.** Covered: corridor, tunnel and toll topologies. Missing: connected vehicle (SPaT/MAP), preemption/TSP, ramp metering, freeway VDS, adaptive control, center-to-center, cellular backhaul, smart city.
- **Only one ITS attack playbook exists, and its "tamper" stage changes `sysName`/`sysLocation`.** It does not touch signal timing or DMS messages.

The wire-level work rail did for ATCS/EMP (spec-grounded engine, `SPEC_NEEDS.md`, labeled-corpus sidecar, DPI parser guide) has no NTCIP equivalent yet. That is the largest depth gain available.

## 1. Validation: "NTCIP does not reach the wire"

### Method (executed)

The test script `tasks/audit-results/its-ntcip/e2e_ntcip.py` (run recipe in that folder's README) runs the real pipeline. Nothing was mocked in the flow path:

1. `generate_from_archetype("transportation_atms_corridor", scale="small")`
2. `auto_repair_protocols`, then `repair_flow_protocols`
3. `traffic_generator.tasks._build_flow_contexts` (the same builder PCAP jobs use)
4. `UnifiedOrchestrator` + `PcapOutput` for 30 s of virtual time
5. Decode the PCAP with scapy and count response varbinds by destination role

### Result: baseline (as shipped)

The scenario had 21 devices and 32 flow contexts, 22 of them SNMP, and produced 3,058 packets. The SNMP flow `config` keys were `_vertical`, `matrix_origin`, `pattern` and `phase_tags`. No flow had `device_type` or `poll_oids`.

| Responder role | OIDs returned |
|---|---|
| traffic_controller | `1.3.6.1.2.1.1.{1,2,3,5,6}.0` only (391 varbinds) |
| cctv_camera, cabinet_controller, core_switch, historian | same five MIB-II objects |
| **NTCIP `1.3.6.1.4.1.1206.4.*`** | **0 varbinds** |

The PCAP is regenerated by running the script; it is not committed.

### Result: counterfactual (forcing `device_type="asc"` on controller flows)

I ran `tasks/audit-results/its-ntcip/e2e_forced.py`. It produced **330 NTCIP varbinds, and every one had value `0`**. All of them sat under `1.3.6.1.4.1.1206.4.2.2.*`. Per the expected arc map below (still to be confirmed against the MIB files), that is NTCIP 1207 ramp meter control, not 1202 ASC. The objects are also invented `.0` scalars rather than table columns.

**Conclusion:** propagating `device_type` alone would make the demo *worse*, because it would put zero-valued, mis-arced OIDs in front of a DPI tool. The fix has to land as one unit (plan, Phase 0).

### Statically confirmed (not executed)

- **Hand-authored templates.** `api/routes/templates.py:734` only uses the archetype generator when a template has no `devices`. All four road templates ship devices and flows. None of their flows carries a `config` with `device_type`, and the create route adds none. Same fallback.
- **Live agent.** The Dockerfile copies `backend/app/protocol_engines/` into the agent image (`docker/packetarch-agent/Dockerfile:43`), so the agent runs the same SNMP engine. `orchestrator_pool.py:862-875` merges no `device_type` into the flow config. The `device_type=` at `:617` is a DeviceInfo field and does not reach the flow.
- **Skipped enrichment.** I did not run `ensure_device_flow_coverage` or `ensure_remote_access_cloud_links` because they need the DB. A grep shows neither sets `device_type` or `poll_oids`.

### Root causes (file:line)

| # | Defect | Location |
|---|---|---|
| R1 | No code path sets `flow.config["device_type"]`/`poll_oids`. `_get_poll_oids` falls back to `DISCOVERY_OIDS`. | `protocol_engines/snmp/engine.py:167-183` |
| R2 | The template `snmp_identity.ntcip_device_type` exists, but its only reader is `identity/snmp_builder.py:218`, which has no caller. | `device_templates/vendors/transportation.py:910` et al. |
| R3 | The OID check is `".1.3.6.1.4.1.1206.4.2.2" in oid`. Stored OIDs have no leading dot, so it never matches and the code falls through to `return 0`. Removing the dot exposes a second bug: `"1.4.1"` is a substring of the root itself. | `engine.py:268, 288, 307, 312` |
| R4 | The NTCIP arc constants assume devices.N = NTCIP 120N. | `protocol_engines/snmp/oids.py:26-32` |
| R5 | Phase reds, yellows and greens are independent `randint(0,255)` calls, so a phase can show red and green at once. The timing plan is random on every poll. The cycle counter counts polls. | `engine.py:270-278` |
| R6 | There is no ESS branch in `_get_poll_oids`, and `get_ess_poll_oids()` is unused. | `engine.py:167-183` |
| R7 | Tests assert the wrong `.4.2.2` root and a range that a constant `0` passes. | `tests/protocol_engines/test_snmp.py:410-419, 1186-1215` |
| R8 | The process sim `traffic_signal` model is never bound to SNMP payloads. `payload_defaults.py:118` returns None for SNMP. | `process_sim/templates/transportation.py` |

| Protocol / object group | Status |
|---|---|
| SNMP v1/v2c/v3, GET/GETNEXT/GETBULK/SET builders | Present (`snmp/packets.py`). Legitimate traffic only ever sends one-varbind GETs. No legitimate SETs. |

| NTCIP 1205/1206/1207/1209/1210/1211/1218 | Absent. |
| NTCIP traps / unit-alarm traps | Absent. Only generic coldStart and linkUp traps exist. |
| SAE J2735 SPaT/MAP/BSM, TSCBM (UDP 6053), IEEE 1609 | Absent. |
| NTCIP 1103 STMP, AB3418 | Absent. |
| NTCIP 2306 / TMDD center-to-center | Absent. |
| RTSP/RTP/ONVIF | Absent. `rtsp` and `ntcip` appear in comm-matrix entries but are not `ProtocolType` members. The agent drops those flows at `orchestrator_pool.py:783-786`. |
| HTTP web UI, Telnet, FTP/TFTP database transfer, syslog | Absent as engines. FTP appears only in attacks. |
| Modbus/BACnet (tunnel) | Present via the generic engines, but only in the hand-authored tunnel template. |
| NTP | Ambient only. |

**Wire-quality nits:**
- Startup responses use a random `dst_port` instead of the request's source port, so the transactions don't pair (`engine.py:398, 410`).
- `sysUpTime` uses wall-clock time, not virtual time, so PCAP mode shows near-zero uptime (`engine.py:185-189`).

**Scenario defects:**
- **B1. Two sources of truth.** The template list summary calls `generate_from_archetype` (`scenario_templates/__init__.py:77`), but creation uses the hand-authored device list. For `urban_intersection_network` the summary says 69 devices (archetype LARGE), while creation yields the hand-authored set: 13 device entries in the template, expanded by count. Highway and urban map to the *same* archetype at the same scale.
- **B3. Duplicate controller polls.** `find_entries` returns both the vertical and the SHARED `scada_primary→traffic_controller` entries (`comm_matrix/_base.py:162-173`). The corridor at large scale emits 10 duplicate 1 s poll pairs.
- **B4. The archetype corridor drops gear.** It has no detector, RWIS, ANPR or RSU slots. The "aux" `cabinet_controller` is pinned to traffic controllers (`vendor_pinning.py:622`), so each cabinet fingerprints two controllers.
- **B5. The TMC is pinned to Schneider Geo SCADA and EcoStruxure** (`vendor_pinning.py:629-633`). Tunnel and toll reuse the intersection process-sim descriptor verbatim.
- **B6.** `audit_irrational_flows` flags `engineering_workstation→cctv_camera` (info level).

### Attack use cases

There is one ITS playbook: `its_signal_disruption` (`attacks/playbooks.py:1960`). It runs recon, community brute-force, a MIB walk, an SNMP SET tamper and a trap flood. All its handlers exist and run. But the SET stages (`:2134`, `:2155`) write `sysName`/`sysLocation`, so a sensor sees an identity change, not timing or sign manipulation.

The following are missing. They are realistic for detection validation and anchored in public research: Cerrudo/IOActive 2014 (Sensys), Ghena et al. 2014 "Green Lights Forever", the 2006 LA signal sabotage, public DMS-hijack incidents, and ICSA-23-026-01 (Econolite EOS).
- Default-community read, then write
- NTCIP 1202 pattern, flash or force SET
- NTCIP 1203 MULTI message write plus activate ("zombie sign")
- Controller database download via FTP/TFTP
- Preempt spoofing
- Rogue RSU / spoofed SPaT
- Camera compromise
- Cellular-modem pivot
- TMC ransomware

## 5. Lessons from rail worth reusing

Rail (EMP and ATCS, merged to master) established a depth method that roadway lacks:
1. Spec-grounded wire layouts emitted by a dedicated engine.
2. `SPEC_NEEDS.md` listing unknowns and confidence tiers.
3. A labeled-corpus sidecar (`protocol_engines/label_sidecar.py`) for per-packet ground truth.
4. A DPI parser guide (`docs/rail-protocols-dpi-parser-guide.md`).

NTCIP 1202/1203/1204 should follow the same pattern.
