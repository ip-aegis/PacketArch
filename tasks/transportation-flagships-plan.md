# Transportation flagship demos: plan

**Date**: 2026-10-21
**Ask**: transportation demos that are world class: bigger, more complex, more comprehensive. New vendors, devices and protocols are allowed. Existing archetypes don't constrain the design.
**Inputs**: `docs/ITS_ROADWAY_AUDIT_2026_10.md`, `tasks/its-roadway-remediation-plan.md`, two research passes on 2026-10-21 (emit inventory, template machinery). I spot-checked the key claims below.

**Framework defects that would undermine any demo** (verified):
1. **Every curated device name is overwritten with a garbled one.**
   - The create route stores the role as `architecturalRole`, but the renamer reads only `architectural_role` or `role`. It falls back to the display text and keeps 6 characters.
   - Example: `TMC_ATMS_Central_Server_1` becomes `TX130-TOLL-TRAFFI-001`. Names can contain spaces (`RADAR -004`) and collide (`DYNAMI-003-2`).
   - Code: `site_naming.py:163-173`, `templates.py:385`.
   - **This affects every vertical.**
2. **The audit and the template card show a different scenario from the one creation builds.** `template_definition_builder.py:89` lacks the "no devices listed" guard that `templates.py:734` has.
3. **Flow `config` is hard-coded to `{}`** (`templates.py:680`). Templates can't set an NTCIP profile, SNMP version, hostname or TLS.
4. **Round-robin type expansion can't express real fan-out or per-cabinet pairing.**
   - Two redundant ATMS servers split the controllers between them, instead of both polling all of them.
   - A cabinet's controller isn't tied to its own detector or MMU.
   - The expander is duplicated in four places.
5. **Template fields that are silently ignored:** `process_sim` (the vertical picks the model), `phase_preset` (the wizard hard-codes `standard`), and `recommended_attack_playbooks` (never read).

**Capability ceiling** (from the emit inventory):
- **Engines:** NTCIP 1201/1202/1203/1204 are real now. Modbus, S7, ENIP, BACnet, DNP3, OPC UA, EMP and ATCS are solid.
- **Shape only:** HTTPS, SSH, Telnet and RDP are a TCP or TLS session with no application payload.
- **Missing protocols:** HTTP/VAPIX, RTSP, syslog, DNS, FTP/TFTP, SPaT/MAP.
- **Missing device classes:** ATMS central, MMU, video detection, V2X RSU, cellular routers, routers/firewalls, VMS, travel-time readers, EVP/TSP, tunnel sensors.

## 2. How to build them

- **Hand-authored flagship templates, generated by factory functions** in one module per flagship, for example `cabinet(i, hub, vendor_mix, fw_pin)` and `hub(j)`. Each returns explicitly named single-device specs plus grouped flow specs.
- Flagships are **not** mapped in `LEGACY_TEMPLATE_ARCHETYPES`, so the card count, the audit and the created scenario all agree.
- Archetypes stay for the AI designer and get improved separately.
- **Zone model:**

  | Zone | Level |
  |---|---|
  | Enterprise / cloud | 4–5 |
  | IDMZ | 3.5 |
  | TMC | 3 |
  | Field hubs, each grouping 5–8 cabinets | 2 |
  | Cabinets, as device groups inside the hubs | 1 |

  - Keep about 12 zones or fewer, so multi-sensor deployment stays around 16 GB.
  - Use `cell_isolation: conduit_gated` with explicit conduits.
- **Every flagship ships with** a per-template test (in the style of `strict_purdue`) and a **demo runbook** (`docs/demos/<flagship>.md`). The runbook gives the story, what to show in Cyber Vision, which playbook to run, and the expected detections.

**Security testing:** each flagship lists the existing playbooks that apply and the detections a sensor should raise. No new attack content is in this plan.
