v1.10.0
2026-06-17
OT Intelligence
IEEE-grounded vendor OUIs and Cyber Vision provisioning overhaul
New & Improved
  • IEEE-grounded vendor OUIs. VENDOR_OUIS is now auto-generated from a bundled IEEE registry (protocol_engines/data/ieee_oui.csv) by scripts/generate_vendor_ouis.py. All 326 device templates were rewritten to their vendor's authoritative OUI. get_vendor_for_oui() returns the exact IEEE registrant name Cyber Vision uses internally — eliminating mislabeling (e.g. Yokogawa analyzers appearing as “Siemon”). A CI guard, tests/test_oui_data_integrity.py, prevents future OUI drift.
  • CV group naming overhaul. Provisioned groups now use readable bare zone names with deterministic cross-scenario deduplication and correct acronym casing (app/core/name_normalize.py). A new POST /api/v1/cyber-vision/reconcile endpoint lets operators re-run normalization against a live CV center without redeploying.
  • Vertical roll-up presets. provision_vertical_preset / reconcile_vertical_presets accept multiple subnets in a single call. Presets reconcile automatically on scenario create and delete.
  • Ghost purge on scenario delete. Teardown now best-effort deletes the scenario’s CV components and devices by MAC address, keeping the CV device map clean after scenarios are removed.

v1.10.1
2026-06-19
Patch — OVA Appliance
Three OVA appliance bugs fixed: BIOS boot, console user, local-lab agent registration
Bug Fixes
  • BIOS boot failure. OVAs without an explicit OVF firmware attribute dropped to grub rescue> on BIOS hypervisors. Fixed in build-ova.sh by installing grub-pc-bin and running grub-install --target=i386-pc. The appliance now boots under both BIOS and UEFI.
  • No console user. The Ubuntu cloud image creates its user via cloud-init, which is disabled in the seedless OVA. The previous --password virt-customize flag was a no-op against a nonexistent account. Fixed with explicit useradd + chpasswd + sudo grant.
  • Local-lab agent registration. The on-box local-lab agent phoned home to site.fqdn, which is frequently unresolvable from inside the appliance (no internal DNS, NAT hairpin). The agent now uses https://127.0.0.1 with an optional local_sensor.server_url override. CV sensor enrollment is unaffected.
v1.11.0
2026-06-29
AI & Reliability
Async AI device naming with provisioning gate, CIRCUIT model update, and platform reliability improvements
New & Improved
  • Asynchronous AI device naming. Creating a scenario from a template previously ran LLM site-identity generation and descriptive device naming inline (2–3 minutes total), exceeding upstream proxy timeouts (Cloudflare caps at ~100 s). The scenario now commits immediately with deterministic site-rail names (naming_status: pending). The LLM overlay runs in a Celery task (apply_template_naming) and writes names back when done. This also eliminates FK violations where audit rows were committed before the scenario row existed. A NamingProgressModal gates the Studio until naming succeeds.
  • Provisioning gate. Deploy (agents) and PCAP generation return 409 Conflict while naming_status is pending or running. POST /scenarios/{id}/naming/retry re-triggers a failed run; reconcile_pending_naming() requeues any scenarios left in-flight after a restart.
  • OT Engineering Workstation fingerprint. A new device fingerprint models a Windows host running vendor PLC-programming software: EtherNet/IP, S7comm, and OPC-UA alongside RDP, HTTPS, and SNMP, with Microsoft Windows OUIs. The ev_battery_cell_plant template now uses this fingerprint with realistic cross-vendor programming flows.
  • CIRCUIT model default: gpt-5-nano. The .env.example previously shipped CIRCUIT_MODEL=gpt-4.1, which was removed in March 2026. New installs now default to gpt-5-nano. gpt-4.1 and gpt-4.1-mini are labeled “(deprecated — removed Mar 2026)” in the CIRCUIT model picker.
  • Nginx no-cache for index.html. Served with Cache-Control: no-cache while hashed asset bundles remain immutable. Operators behind CDNs pick up new frontend deploys reliably without cache purging.
  • Scenario template hygiene. All 32 CI-tested scenario templates are lint-clean: zero orphaned devices, all flow protocols declared on both endpoints. Fixes covered semiconductor fab OPC-UA/KUKA mismatch, EV battery cip_motion non-existent type, and fulfillment center WCS Modbus undeclared protocol.
Bug Fix
  • Host-agent crash loop from stale bind mount. The host-agent used a relative bind mount for live-editing convenience. When recreated from a different or absent directory, Docker silently created an empty directory at the stale path and mounted it over /app, producing a ModuleNotFoundError crash loop that silently blocked all local-lab provisioning. The shipped compose no longer includes this mount; a docker-compose.host-agent-dev.yml overlay is available for development.
Infrastructure
  • OVA build on self-hosted KVM runner. The build-ova CI job now targets a self-hosted runner labeled ova-builder, replacing the unstable GitHub-hosted path. OVA artifacts attach to every draft release; if the runner is offline the job queues while bundle jobs continue to publish.
v1.12.0
2026-07-01
Attack Simulation & Protocol
Attack PCAP export with split artifacts, kill-chain timing fix, and BACnet on-wire corrections
New & Improved
  • Attack PCAP export — split artifacts. A single generation run now emits three PCAP files via SplitPcapOutput: combined (all traffic), baseline-only, and attack-only. Controlled by GenerationRequest.export_attack_pcap; downloaded via GET /generation/{id}/download?artifact=. The frontend adds a toggle and per-artifact download buttons.
  • Local-sensor agent-update reliability. A CV sensor failure no longer aborts the reconcile loop. ensure_agent_image now compares the served tarball’s X-Checksum-SHA256 header on each reconcile and refreshes when the served version changes. Build Image triggers an immediate reconcile. The CV sensor compose uses pull_policy: missing to tolerate transient registry hiccups.
Bug Fixes
  • Kill-chain timing in PCAP mode. Attack stages advanced on the wall clock, causing the heap to drain in a fraction of a second in timed PCAP mode — only stage 0’s first actions appeared. PCAP mode now advances on the virtual clock and time-compresses the kill chain to fit the capture window.
  • BACnet on-wire encoding. Two encoding bugs: (1) Status_Flags ReadProperty responses included a spurious length octet; (2) application-tagged primitives ≥128 bytes used ASN.1 BER instead of BACnet extended-length encoding. Both corrected. bacnet_vendor_id drift across building-automation, Honeywell, Schneider, and Siemens templates normalized to the BACnet vendor registry.
  • Attack target resolution in PCAP mode. _resolve_targets() only accepted the frontend device shape; the flat PCAP device representation produced zero targets and zero attack packets. Fixed to handle both shapes. A spurious double-warmup in schedule_initial_events was also removed.
  • Alembic multiple-heads on fresh install. A rebase created two alembic heads with the same parent; alembic upgrade head failed on a clean database, blocking fresh installs and CI. Fixed by re-pointing add_gen_job_artifacts.down_revision to restore a linear migration history.

v1.12.1
2026-07-01
Patch — Agent Distribution
Prebuilt agent image re-served from bundle on boot — no manual “Build Image” required
Improvement
  • Build once, distribute. On boot, startup.ensure_agent_image_current detects when a prebuilt agent image is loaded and is the newest available, then runs docker save to write version.txt and the SHA256 checksum — exactly as an in-app build would, but in ~4 s with no source required. Source rebuilds are still performed when the agent source is strictly newer (development installs).
  • Dockerfile version label. The agent Dockerfile now stamps org.packetarch.agent_version via an AGENT_VERSION build-arg, allowing the server to read a loaded image’s version without any source files.
Agent
  • Agent bumped to v2.2.1 (packaging label change only — no protocol or behavioral changes).
v1.12.2
2026-07-01
Patch — Agent Distribution
GHCR registry channel completes zero-touch agent updates for all install types
Improvement
  • Three-path agent distribution. v1.12.1 covered offline bundles and source-mounted dev installs. Internet-connected installs with neither had no automated path to a new agent. All three paths now auto-serve on boot, firing the update banner with no manual “Build Image” and no compose edits:
    • →Offline — re-serve the bundle image
    • →Online — pull from ghcr.io/<owner>/packetarch-agent:<version>
    • →Development — build from source (unchanged)
  • GHCR publish in release pipeline. release.yml pushes the agent image to ghcr.io/<owner>/packetarch-agent as both a version tag and :latest on every v* tag (full variant only). Note: the GHCR package is private on first push — publish it publicly once so unauthenticated installs can pull without credentials.
  • Offline install guard. The bundle installer writes AGENT_REGISTRY_PULL_ENABLED=false into the generated .env so air-gapped hosts never attempt a registry pull.
v1.13.0
2026-07-02
Cyber Vision
Cyber Vision network organization — scenario /16 and per-zone /24 networks provisioned at deploy
New & Improved
  • CV network provisioning. When a scenario is provisioned to Cyber Vision, PacketArch now defines its network organization: one custom network for the scenario’s /16 range and one /24 per zone, using the same zone labels as the group names, all typed OT Internal. This segments the CV topology map by scenario and zone instead of lumping all simulated traffic under the built-in 10/8 catch-all.
  • Idempotent and safe. provision_networks() uses get-or-create keyed by IP range; runs synchronously at deploy with no device-aggregation wait. Teardown deletes only the scenario’s own networks, scoped strictly to ranges within the scenario’s /16 — built-in networks and other scenarios are never touched.
  • Frontend network visibility. The DeploymentPanel surfaces provisioned networks — a count and per-range tooltip. CVProvisionStatus carries a networks map for at-a-glance status without opening the CV center.
  • Reconcile endpoint. reconcile_cv_networks() is wired into POST /api/v1/cyber-vision/reconcile so operators can re-sync network definitions after manual CV edits without redeploying the scenario.
